# Decisions

- Commits are made as repo-local identity `elsiribot` because no git identity was configured.
- `scripts/screenshot.sh` builds the binary before starting sway, so the 15 s window-map timeout excludes compilation.
- `just screenshot` writes to `target/screenshots/<name>.png`, which is already gitignored via `/target/`.
- Screenshot harness waits for sway app_id `fedimix` (what GTK reports under headless sway), not the reverse-DNS application id.
- `Amount::from_sat` saturates: valid amounts never reach `u64::MAX` msat, but user input must not panic.
- `EventStream` derives Clone (async_channel receivers are cloneable): clones share one queue and split the events, so independent consumers call `subscribe()` instead.
- tokio began as a dev-dependency of core; it is now a regular dependency (features sync, time) for the demo backend, and the `Backend` trait stays runtime-agnostic.
- DemoBackend keeps event senders in a separate std Mutex (not the state Mutex) because `subscribe()` is sync and must also be reachable from the delayed-notification task; each subscriber gets its own unbounded channel and closed ones are pruned on emit.
- `SendConfirmed` is emitted via `tokio::spawn` + sleep only when a tokio runtime is current; without one it is skipped rather than panicking.
- Demo refill checks the signing device before the target gap, so NoSaving reports NotSetUp rather than "at target"; `prepare_exit` (the quote, not `exit_now`) also requires a device.
- Task 4: `queue_row` takes the anonymity target as a parameter for the meter; caption fraction is for_spending/target below target, else for_spending/(for_spending+moving); `format::date` computes the local UTC offset via glib and delegates to a pure `date_with_offset` so tests are timezone independent.
- Task 5: core runs on a multi-thread tokio runtime (spec section 3) parked on its own "fedimix-core" thread (`block_on(pending)`), because fedimint uses `block_in_place`; `CoreBridge::call` returns results through a bounded async-channel consumed by `glib::spawn_future_local`, keeping callbacks `!Send`.
- Task 5: `AppContext::refresh` goes through the pure `RefreshGate`: one fetch at a time, a burst of events collapses into one follow-up, and results older than the newest applied one are dropped; fetch errors toast. `on_snapshots` has no unsubscribe: callers capture weak refs and dead views no-op.
- Task 5: initial tab is chosen from the first snapshot (Saving unless no Saving device, then Spending), so the window shows Saving briefly before switching in the no-saving case. The Settings and About menu entries open their pages.
- Task 6: `AppContext::on_snapshots` callbacks return `bool` (false = unsubscribe) so dead views are pruned instead of accumulating. `SavingTab` state (`Inner`) is owned by its root widget via a `connect_destroy` closure and subscribed to weakly, so callers need not keep the handle; `Inner` holds only child widgets to avoid a cycle.
- Task 6: A nested change row is drawn inside its parent's `ListBoxRow` (dim caption, indented) rather than as its own row, so it has no card/separator of its own. The Saving page rebuilds only when `SavingState` differs from the last rendered one.
- Task 6: Added `pango` to the flake's `buildInputs` (hence `LD_LIBRARY_PATH`): ellipsizing labels links libpango directly, and the binary failed to load in the dev shell without it.
- Task 7: `--demo-page saving` forces the Saving tab even without a device (to screenshot the empty state); `apply_start_page` runs once after the first snapshot and picks the tab plus any pushed page. `FedimixWindow::new` now takes the start page and holds `AppContext` in an `Rc` shared by all views.
- Task 7: Pushed pages (Coins, coin detail, Notes) own their `Inner` via `connect_destroy` on the `NavigationPage` and subscribe weakly, so a popped page is pruned on the next snapshot. Coin detail's Freeze switch ignores changes it makes itself while syncing from snapshots and reverts with a toast if `set_coin_frozen` fails.
- Task 7: "Anonymity at exit" on coin detail is derived from the privacy tag (`~N`, `~N (early exit)`, `None (unmixed)`, `None (small change)`) since `Coin` carries no separate field; the Spending bar uses `LevelBar` with the default low/high/full offsets removed so it stays accent-coloured.
- Task 8: The anonymity target for the level bars comes from `core().settings()` fetched when the page opens (spec default 50 until it returns). The dialog is parented on the nav view (rows are rebuilt on each snapshot).
- Task 9: `qr::matrix` returns `Result` (data over QR capacity is an error, not a panic) and the QR is always black modules on a white 4-module quiet zone so it scans in dark theme; `qrcode` is used with default features off. Send validation errors stay quiet until an amount is typed; above-balance is reported inline from `prepare_send`'s `InsufficientFunds`. A destination that carries an amount hides the amount field. Confirm goes insensitive (with spinner) before `confirm_send`; an in-flight guard makes double activation send once. The Receive switcher is a `gtk::Stack` + `StackSwitcher` (titles only; `ViewSwitcher` needs icons). `--demo-page send|receive` open the Spending dialogs, `send-review` drives the Saving review with a demo address.
- Task 10: The Refill dialog reuses `present::confirm_button(Saving, device)` for the confirm label/sensitivity and follows device changes via snapshots while open, because the refill is signed on the Saving device. The outcome comes from the operation event; double confirm is impossible since AlertDialog closes on response.
- Task 11: The window swaps Join and tabs on every snapshot via a dedicated subscriber that stays subscribed (`federation.is_some()`), separate from the one-shot start-page pick; Join hides the tab switchers but keeps the header menu. The Spending Offline banner shows only for `Some(f) if !f.online`. Settings writes are debounced 400 ms after the last edit (one `set_settings` per burst); handlers connect after the initial values are set, so loading never writes. `present::settings_from_form` also range-checks the spin values; `--demo-page join` pushes the add-federation page.
- Every core error reaches the user through one function, `present::user_message`; `FedimixError` payloads are sentences so it can show them as they are.
- Task 12: The demo driver lives in the binary (`demo_drive.rs`) and matches controls by visible label (buttons, check buttons, switch rows, activatable rows, tooltips for icon buttons, `Back` pops the deepest pushed page, tab names fall back to the ViewStack pages); header and item menus are opened with `action <app.name>` and by clicking the MenuButton's tooltip. `shot` waits for a line on stdin (10 s cap) unless stdin is a terminal, then a fixed 500 ms; `interact-demo.sh` feeds it from a FIFO so each grim capture happens while the app is paused.
- Final fixes: `parse_destination` accepts bech32 addresses only (no base58, as before); checksums wait for the real backend. An invoice's amount comes from its human-readable part. BIP21 `req-*` parameters make a URI invalid, as BIP21 requires. `SendAmount::FromInvoice` also covers BIP21 amounts, since both are "the amount the destination carries". An amountless invoice is `Exact`; `Exact` that differs from a carried amount is refused.
- Final fixes: the Send form's Max button writes `max` into the amount field and `present::send_amount` reads it, so the form has one source of truth. `fee_rate_sat_vb` is API only: the GTK form passes `None` until the Saving wallet has real fee estimates to offer.
- Final fixes: `exit-deferred` is an extra demo scenario, so every `DeferReason` and history status has something to render. `Offline` defers its whole queue with `DeferReason::Offline`. "Exit now" stays available for the fee guard (a manual exit overrides that automatic pacing, spec "Early exit") and is disabled during the online grace period, when offline, and when Spending cannot pay the fee. The grace period has no override (spec section 1: no exit within 10 minutes of starting or reconnecting), so `GracePeriod` is refused in the core (`prepare_exit` returns `FedimixError::GracePeriod`) as well as in `present::exit_allowed`.
- Final fixes: demo operations run on their own tokio task through `DemoTiming` (300 ms per state; tests pass 1-5 ms), so the demo backend now needs a tokio runtime for confirm calls. Money moves at the end of the operation; `Exit` marks its item `Withdrawing` from the start so it cannot exit twice. Saving send and refill go AwaitingDevice, Signing, Broadcasting; Spending send and exit go straight to Broadcasting (exits need no device, spec section 4).
- Final fixes: `cancel_operation` is a request: after Broadcasting the operation runs on and reports `Done`. It errors only for an unknown id. Confirming a preview whose operation was cancelled returns `FedimixError::Cancelled`.
- Final fixes: `discard_preview` ignores unknown ids, because walking away must never fail.
- Final fixes: operation events can overtake the reply carrying the id, so `OperationTable` keeps the latest state for a late watcher, and at most 32 unclaimed final states. Watchers live in the context, not in widgets, so an outcome is never lost with a dialog. A failed, cancelled or expired send returns to the Send form with the message inline, since the preview is used up and Review makes a new one. Refill and exit dialogs are alert dialogs that are gone by then, so a late `PreviewExpired` there is a toast.
- Final fixes: `adw::Toast` queues, so outcomes use `toast_now` (high priority) to overtake "Refill started".
- Final fixes: the refill fee is counted when selecting coins and in the overshoot. Overshoot joins the queue split into 1-2-5 denominations; a remainder under 0.001 BTC stays in Spending, because no denomination fits it.
- Final fixes: the demo hands out a new address per on-chain receive, so a real address leak would show. Invoices last an hour (`INVOICE_EXPIRY_SECS`); the Receive dialog has no expiry field.
- Final fixes: server URL and proxy apply through `AdwEntryRow`'s apply button, and the server type applies when picked; debounced writes carry the network values in force, not the fields. Esplora takes `http(s)://host[:port][/path]`, Electrum `ssl|tcp://host:port`, the proxy `[socks5://|socks5h://]host:port`.
- Final fixes: an invalid Settings form cannot be popped (`can_pop` false, so no Back button), because Adwaita offers no veto once a pop starts; a banner states the problem and offers Revert to the values in force, so the page is never a dead end. A valid edit that was not applied is dropped by Back, as Apply is explicit.
- Final fixes: `nix build` sets the GTK runpath itself (`patchelf --add-rpath`), because Rust links without one and the wrapped binary only ran inside the dev shell; an install check that expects exit 2 keeps this from regressing.
- Phase 2 Task 1: `CoreBridge::call` takes `Result` futures and always runs `on_done`; a panic or cancelled task becomes `FedimixError::Internal("Something went wrong inside Fedimix.")`, so a refresh gate, a locked dialog or the Refill claim cannot be left held by a panic.
- Phase 2 Task 1: a Send may be closed after `SEND_LOCK_TIMEOUT` (30 s) in Broadcasting, because a real payment can hold for hours. The dialog does not close itself; the caption says the result will appear, and the operation watcher (which outlives the dialog) toasts Payment sent, or the failure. The timeout runs from Broadcasting, not from Confirm, since before that Cancel is available and the device flow is short.
- Phase 2 Task 1: `DemoTiming` gained `broadcast_hold` (extra time in Broadcasting) and `send_lock_timeout` (an optional override for the front end's wait); the `send-stuck` scenario sets 4 s and 2 s so flow 20 does not wait 30 s.
- Phase 2 Task 1: a failed first snapshot shows an error page with Retry (a toast would leave the spinner up for good); later failures stay toasts, since the tabs are still there.
- Phase 2 Task 1: in Settings, the URL's Apply and the server type write the server (type and URL together, since a URL is only valid for its type) with the proxy as in force; the proxy's Apply writes the proxy with the server as in force. An unapplied edit in the other row is never sent.
- Phase 2 Task 1: the Receive dialog's Retry button holds the payload view through weak references, and the Send review's `Progress` holds its widgets weakly, so neither dialog is kept alive by its own closures. Editing the invoice description makes the shown invoice stale like editing the amount.
- Phase 2 Task 1: the driver gained `expect-disabled` / `expect-enabled <row text>`, because a disabled menu button cannot be clicked and the flow has to assert that it is off.
- Phase 2 Task 2: fedimint is a workspace dependency of `fedimix-core` as dev-dependencies only (the smoke test); `fedimix-gtk` does not depend on it. Reason: nothing real uses it yet, and the plan has the real backend arrive later.
- Phase 2 Task 2: the `integration` shell exists so plain `nix develop` neither builds fedimint nor needs `--accept-flake-config`; the `fedimint` input has no `follows`, so its binaries match the cachix cache.
- Phase 2 Task 2: `nix flake check`/`nix build` set `LIBCLANG_PATH` and add clang, cmake and protobuf because librocksdb is compiled from source; libstdc++ goes on the runpath and on `LD_LIBRARY_PATH`.
- Phase 2 Task 3: public api types (`Amount`, history types, `Settings`, `ChainBackend`) derive serde, so history and settings are stored as JSON in one column; amounts stay msat integers. Reason: no hand-mapped twin types to keep in sync, and the FFI shape is unchanged. History keeps indexed wallet, federation_id, timestamp and id columns for paging.
- Phase 2 Task 3: the data folder lock uses `std::fs::File::try_lock` (flock) instead of a crate, and `Seed` stores the phrase through the bip39 type that `fedimint-bip39` re-exports; `fedimint-bip39`, `fedimint-client` and `rand` moved from dev-dependencies to dependencies. `root_secret()` waits for Task 5.
- Phase 2 Task 3: `upsert_history` keeps the stored timestamp of a known id (the update changes status and content, never the row's place), and `history_page`'s `before` must be a stored id or it returns `UnknownItem`. Saving rows pass `federation_id: None`, stored as an empty string.
- Phase 2 Task 3: `FederationRow` carries `balance_msat` (last known balance while offline) and the store gained `active_federation()` so `set_active` can be read back. A seed file with group or other bits is refused with a `chmod 600` sentence, never repaired; creation goes through `seed.tmp`, fsync, rename, fsync of the folder.
- Phase 2 Task 3 fix: history is addressed by `(wallet, federation_id, id)` everywhere, including the `before` cursor; `history_page` takes `federation_id` (`None` for Saving), because the UI shows the active federation only and a second joined federation must not leak into it.
- Phase 2 Task 3 fix: the data folder is created 0700 and `fedimix.db` 0600 before SQLite opens it (SQLite gives -wal/-shm the db's mode); an existing folder open to group/others is refused with a `chmod 700` sentence, never repaired. `Seed::load_or_create` takes `&DataDirLock` and publishes with `hard_link`, so an existing seed is adopted, never replaced.
- Phase 2 Task 3 fix: `Settings` is `serde(default)` so older rows load; a history row that no longer parses is skipped with an stderr warning (no tracing dependency yet). Writes use `Immediate` transactions, `synchronous=FULL`, and open fails if WAL did not take effect. Migrations run as a loop in one transaction.
- Phase 2 Task 4: `history(wallet, before, limit)` takes a row id as the cursor and returns `UnknownItem` for one that is gone; Spending covers the active federation only. Snapshots keep the newest `SNAPSHOT_HISTORY = 50` rows. The UI offers "Show more" on a full snapshot (it cannot know more exists), and drops the pages it loaded when a snapshot's row ids change, because a new row pushes the last one out of the snapshot and the pages would skip it; a status change keeps them.
- Phase 2 Task 4: the demo's `recovery_words` is twelve times "demo", which fails BIP39 so it cannot pass for a seed; the page does not care. `shutdown` is a no-op. Quit and the window's close button both wait for `shutdown`, at most 30 s (`bridge::capped`, `SHUTDOWN_CAP`), then quit; the driver ends scripts through the quit action so that path runs in every flow.
- Phase 2 Task 4: `Event::Operation.history_id` is set on the `Done` event only, to the first history row the demo operation made (Send: its row; Refill: the Saving row; Exit: the Spending row). `operations()` at startup gets a toast-only watcher per running operation (`present::resumed_outcome`), as its dialog is gone.
- Phase 2 Task 4: `validate_address` takes the public `Network` and uses `bitcoin` inside only; `parse_destination` stays lexical and accepts base58 by shape (first char `1 3 m n 2`, 26-35 base58 characters, case kept). `FederationInfo.balance` in the demo is read from Spending's balance when asked; the fixtures hold zero.
- Phase 2 Task 4 (review Minor 1-3): `Network::with_edit` decides which network values an Apply writes (the edited ones, the rest from those in force) and is unit-tested, so applying one row never clears the proxy. The Send review's `closed` is also set when its page is left, and `Done` then no longer closes the dialog. The panic reason is "a background task stopped.", so the user text no longer says "Something went wrong" twice.
- Phase 2 Task 4: the driver gained `scroll-end` (scroll visible scrolled windows to the bottom), so "Show more" can be screenshotted below the fold.
- Phase 2 Task 5: RocksDB, not cursed-redb, for client DBs: `MemAndRedb` keeps the whole database in RAM and is the wasm path. Both module generations are supported, because 17 of 21 listed mainnet federations run v1 and new 0.13 federations default to v2.
- Phase 2 Task 5: `FederationPort` and `Seed` stay out of the documented API, but `tests/devimint.rs` is another crate, so they are `pub` and re-exported from `#[doc(hidden)] fedimix_core::testing`. A cargo feature would hide the tests from `just clippy`. Nothing in `testing` names a fedimint or bitcoin type, and `Seed::root_secret` stays `pub(crate)`.
- Phase 2 Task 5: streams run as tasks owned by the client wrapper and feed a channel, so a consumer's stream holds no client reference. `shutdown` can then end them and release RocksDB, which `open` needs again in the same process.
- Phase 2 Task 5: calls that only read time out after 20 s as `Offline`, because fedimint's requests retry for ever. `pay_invoice` and `withdraw` have no timeout: an interrupted payment must not read as one that never started.
- Phase 2 Task 5: v1 reports `Confirming { confirmations: 0, required }` until the federation claims, then `{ required, required }`: `DepositStateV2` has no count, and `required` is `finality_delay + 1`. The UI cannot show a rising count on v1.
- Phase 2 Task 5: v2 `deposits()` reads the client's event log itself instead of calling `await_receive`, which yields no amount: `ReceivePaymentEvent` gives value, fee and outpoint, `ReceivePaymentUpdateEvent` gives the outcome, and the operation's meta supplies the amounts when a resumed cursor skipped the first. It then waits for issuance as `await_receive` does. Cursor 0 replays everything, so no position needs reading before `receive()`. `DepositEvent.id` is the outpoint, so a retried claim keeps its row.
- Phase 2 Task 5: an amountless invoice is an `InvalidAmount` at `lightning_quote`, whatever amount the caller wants, because LNv2's `send` has no amount to give. A testnet federation previews with `network: None`, which no `Network` equals, so join refuses it. An already initialized client DB makes `join` open it, because joining twice with one secret ruins a wallet.
- Phase 2 Task 5: a `Settled` send waits for the change notes first (LN and v2 withdrawals; v1's stream already does), because fedimint reports success while change is still being issued and the balance reads thousands of sat short for a moment. Reason: `Settled` must mean the balance is whole.
- Phase 2 Task 5 fix: `scripts/fund-gateways.sh` pegs in every vetted gateway without ecash before the tests, because `dev-fed` funds only two of the three and an empty gateway cannot fund an incoming contract. `pay_with_lnd` then retries only for LND's own gateway ("self-payments not allowed"): 8 tries, not the plan's 3. The product still passes `None`.
- Phase 2 Task 5 fix, known limit: a vetted gateway short of ecash fails receives. `RoutingInfo` has no liquidity field and `receive(None)` skips only offline or receive-disabled gateways, so with one depleted gateway among N about 1 in N invoices cannot be paid; the payer sees a failure and the receive ends `Expired`. A new invoice may land elsewhere.
- Phase 2 Task 5 fix: `LightningQuote` carries the invoice, gateway and terms, and `pay_invoice` takes the quote and calls `send_with_terms`, so the fee shown is the fee charged. `TermsChanged` is `PreviewExpired`, so the UI previews again. Gateway choice at quote time stays `None`.
- Phase 2 Task 5 fix: `pay_invoice` and `withdraw` take an `intent` stored as `fedimix_intent` in the operation meta, and `find_operation` reads the newest 1000 operations for it. Reason: the op id only exists after submission, so Task 8 writes the intent first; after a crash, found means resume and not found means never submitted.
- Phase 2 Task 5 fix: a v1 deposit at or below `peg_in_abs` ends `Failed`, not `Settled`: the client records such a claim as done with no ecash and the state still reads `Claimed`.
- Phase 2 Task 5 fix: `Refunded` also waits for the funding transaction's change, as `Settled` does, so a final update always leaves the balance whole. Operation details that cannot be read give a `Failed` sentence, never `Settled` with zero.
- Phase 2 Task 6: `federation/fake.rs` sits behind a `testing` cargo feature, not `cfg(test)` as the plan said, and `testing::real_backend(config, port, clock)` exposes `with_port` under it. `tests/real_backend.rs` is another crate and sees no `cfg(test)` code. Only fedimix-core's dev-dependency on itself turns the feature on, so `cargo test` and `cargo clippy --all-targets` have it, and resolver 3 keeps it out of a normal build.
- Phase 2 Task 6: a set proxy gives `FedimixError::ProxyUnsupported`, a full sentence, instead of the plan's `Offline`, which would tell the user to check their connection. One `Gate` (`Open`, `Proxy`, `Stopped`) in a watch channel drives every supervisor and join, so setting a proxy closes running clients and cancels a join in progress, and clearing it connects at once. `FederationInfo.online` reads false from the moment the setting is saved.
- Phase 2 Task 6: each federation has a supervisor that runs the connection as a child task. The client lives in `Core`, not in the child, so a panicking child cannot drop an open client: that would keep its RocksDB open and every later `open` would fail. After a panic or a stream ending, the supervisor closes the client and opens a new one. Backoff resets only after a connection lasted 60 s, so a client that dies at once does not spin.
- Phase 2 Task 6: the supervisor caches `notes` on each balance update, because `FederationClient::notes` is an async client call and no read may await one. `spending_state` shows them only while online.
- Phase 2 Task 6: `add_federation` sets the active flag in its own write when no federation is active, so a crash cannot leave federations with none active. `set_active_federation` still works: "stays the first joined" is about Fedimix not moving it by itself.
- Phase 2 Task 6: `online_at` is the last time a federation went online, or the join. `QueueState.total` is 0, the sum of no items, as in the demo: `SpendingState.moving` reports the amount. `set_settings` enforces the ranges the Settings page offers. After `shutdown` reads still answer but writes are refused, as the folder lock is gone. Dropping the backend without `shutdown` stops the tasks too, asynchronously; only `shutdown` guarantees the lock is free on return.
- Phase 2 Task 6: `discard_preview` succeeds rather than giving `Internal("Not available yet.")`, as walking away must never fail. `operations()` lists running sends since Task 8.
- Phase 2 Task 6 fix: a data folder belongs to one network. `Store::bind_network` writes it to a `meta` row at the first open and refuses another with `WrongNetwork`, before any supervisor starts. Schema v1 changed in place, as nothing has shipped: a development folder from before this must be recreated. Task 8's `validate_address` relies on `CoreConfig.network` being the federation's.
- Phase 2 Task 6 fix, known limit: setting a proxy closes clients, but `FedimintPort` keeps one `ConnectorRegistry` for the process, and connectors it has built (an iroh endpoint, say) stay bound until exit, so "traffic never goes direct" holds fully only for a process that starts with the proxy set. The registry is not rebuilt: closing it reliably is unproven, and fedimint 0.13 has no SOCKS5 option anyway. `AdwEntryRow` has no subtitle, so the group's description carries the caption, which since the Phase 2 final fix says what matters to the user: "With a proxy set, Fedimix stays offline."
- Phase 2 Task 6 fix: `join` of a known federation returns without network, from the id in the invite (`FederationPort::federation_id_of`). The exception is one with no client whose last `open` failed with anything but `Offline`: Task 7 replaced its fresh `port.join` with recovery by the supervisor, so a lost client database is never joined anew. The error reached stderr only until `FederationInfo.problem` (Phase 2 final fix).
- Phase 2 Task 6 fix: `join` reads `client.balance()` once before writing a new row, so joining an existing client database reports its money at once. This is one await with the client outside `Core`; a future dropped there leaves the client to fedimint's own close on drop.
- Phase 2 Task 6 fix: synchronous SQLite behind a `std::sync::Mutex`, on the runtime's workers, is accepted. Each balance change is an fsync and reads wait on the same mutex, so a stalled disk delays reads, but balance changes are rare and GTK has its own thread. If Tasks 7-8 make writes frequent, move the store to one dedicated thread.
- Phase 2 Task 7: a Lightning row and its watch go in one `Store::add_receive` transaction, before the invoice is returned, so no crash leaves a row nothing updates. A deposit row appears on first sight, and an address alone adds a watch on v1 and nothing on v2. v2 rows are `Pending` until the claim is confirmed, because its log gives no confirmation count.
- Phase 2 Task 7: `upsert_history` reports `Added`, `Changed { was }` or `Unchanged`, and `Notice::DepositConfirmed` hangs on that report, because only the store's transaction sees old and new together. A final status is never replaced by `Pending` or `Confirming`, so replaying a watch after a crash between the row and `finish_watch` changes nothing and notifies nobody. A crash right after the write loses that one `Notice`: at most once, and the row is there.
- Phase 2 Task 7: watches run in a `JoinSet` owned by the connection task, so aborting it stops them and the store's list is the only state to resume from. `resume_watches` reads the store once per connect. `receive` hands a new watch over a channel installed before that read, and a set of started ids drops the case where a watch reaches both. Streams hold no client reference. A stream that ends with no final update leaves the row; only the next connect resumes it.
- Phase 2 Task 7: at most `MAX_DEPOSIT_WATCHES = 100` unused deposit watches per federation; adding one finishes the oldest in the same write. A v1 address never expires, so nothing else would end them. A watch with a history row is not unused and is never dropped: it would leave a row at `Confirming` for ever, so the count can exceed 100 by the deposits in flight. A dropped watch's task runs until the connection ends, so if its address is paid meanwhile, the row's write takes the watch back in the same transaction. On a dropped address the client's own monitor still claims a late deposit and the balance reflects it, but it adds no row and no `Notice`.
- Phase 2 Task 7, known limit: a second payment to one v1 address credits the balance but adds no row, because `subscribe_deposit` reads the first transaction of the address and ends. On v1 Receive shows a fresh address every time, so this takes a payer reusing an old one. On v2 the address repeats until a payment to it is seen (`ReceiveInfo.address_repeats`, Phase 2 final fix).
- Phase 2 Task 7: `ReceiveInfo.min_deposit` is the port's value, and it is a floor. On v2 the claim also pays mint fees and `receive_fee` moves with the feerate, so a deposit just above it can still go uncredited, with no row. The Receive text says so since the Phase 2 final fix: "Send well above N; this minimum follows Bitcoin fees." on v2, "Deposits of N or less are not credited." on v1, whose fee is fixed. A v1 deposit at or below the fee reaches `Failed`: row `Failed`, no `Notice`.
- Phase 2 Task 7: a deposit watch that ends `Failed` with no row adds none: the update names no amount, and no row means no deposit was seen. That is what an unused address's watch does after a recovery.
- Phase 2 Task 7: a lost client database is recovered, never joined afresh, which replaces the Task 6 repair through `port.join`: a fresh start from a used seed reuses ecash nonces. `FederationPort::open` answers `UnknownItem` for a missing or uninitialized database, and the supervisor then calls `recover` with the stored invite on its own, without waiting for the user to join again; the seed never used there is safe too, by fedimint's own contract. `join` of a known federation that fails to open now only wakes the supervisor. The port call does not return until recovery ends, so the federation has no client and stays offline meanwhile, and `receive` says `Offline`.
- Phase 2 Task 7: `recover` passes no backup. `download_backup_from_federation` is deprecated, and with no backup fedimint scans: the slice recoveries (mint, mintv2, wallet) ignore the snapshot, and the older history path starts at session 0. v1's mint and wallet are `RecoveryMode::Unusable`, so they join the client only when it is reopened; the port closes and reopens it when `all_modules_usable` is false. walletv2 has no recovery, and its output scanner runs from 0 on an empty database. A recovery cut off by a proxy, a stop or a crash resumes from saved progress on the next `open`; a module that gives up is retried the same way, with the supervisor's backoff.
